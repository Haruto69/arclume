# Arclume Opportunity Source Research

Research date: July 18, 2026

## 1. Title and research date

This document records Phase 15A research for opportunity source ingestion in Arclume. The assessment was performed on July 18, 2026, using official provider documentation, provider-owned repositories, official program pages, and official terms or help-center pages where available.

## 2. Purpose

The purpose of this document is to decide which opportunity sources are safe candidates for later backend ingestion, which sources require provider approval or legal review, and which sources must remain manual outbound links only. It is intended to guide Phase 15B architecture without implementing providers, migrations, configuration, jobs, schedulers, or UI changes.

## 3. Scope

The scope covers remote jobs, job board APIs, programming contests, hackathons, developer events, student programs, education benefits, fellowships, open-source programs, and no-scrape social or unofficial sources.

The research also checks Arclume's current normalized model at a high level. Jobs already include `sourceProvider`, `externalId`, `externalUrl`, `postedAt`, `syncedAt`, and `isActive`. Hackathons include `sourceProvider`, `sourceId`, `externalUrl`, and `active`. Student programs include `sourceProvider`, `sourceId`, `externalUrl`, `lastVerifiedAt`, and `active`. The current model does not consistently include an attribution label, source URL naming, or sync-run tracking across all opportunity tables.

## 4. Engineering and legal disclaimer

This is an engineering source assessment, not legal advice. Provider terms, API access, rate limits, product availability, and attribution rules are time-sensitive. Before any production sync is enabled, Arclume should recheck the official terms, confirm the intended display and caching model, and obtain provider or legal approval where noted.

## 5. Source safety rules

Use official APIs, official feeds, official provider repositories, or manual official links only. Do not infer permission from public page visibility, reachable JSON endpoints, robots.txt, search snippets, educational intent, or competitor usage.

Do not build scraping providers for sites that prohibit scraping, lack a supported public API, expose only undocumented internal endpoints, or provide user-generated listings without clear redistribution rights. Store only the minimum metadata needed for Arclume, preserve canonical outbound links, show required attribution, sanitize imported HTML, and deactivate stale records instead of silently serving old opportunities as current.

## 6. Verdict definitions

- Approved for automatic ingestion: Official sources clearly support automated external integration, display, attribution, rate limits, and caching or storage for Arclume's intended use.
- Approved with mandatory restrictions: Official sources support API or feed integration, but Arclume must follow explicit attribution, backlink, polling, retention, gating, or redistribution restrictions.
- Conditional - API key or commercial review: The API exists, but production use requires OAuth, API keys, commercial review, approval, or provider contact before activation.
- Conditional - terms unclear: An API or endpoint exists, but official terms do not clearly answer display, caching, storage, redistribution, or third-party aggregation questions.
- Manual official links only: Use curated official links and manually maintained summaries; do not automate ingestion.
- Not approved for scraping: Do not scrape public listings or pages; use only official APIs if separately approved in the future.
- Exclude: Do not include as an Arclume source because authority, permission, accuracy, or maintenance risk is too high.

Every source receives exactly one primary verdict in the provider matrix.

## 7. Approved automatic providers

No provider receives the unrestricted `Approved for automatic ingestion` verdict.

The following providers are acceptable automatic-ingestion candidates only under the `Approved with mandatory restrictions` verdict:

- Remotive: API and RSS access are available for developers to share jobs, but Arclume must link back to the Remotive URL, name Remotive as the source, respect the delayed public feed model, avoid registration or email-gated listing display, and avoid onward syndication to third-party job platforms.
- Jobicy: API and RSS access are available for job apps and wider distribution, but Arclume must poll conservatively, avoid content misrepresentation, preserve source links, and avoid distributing listings to external job platforms such as Jooble, Google Jobs, or LinkedIn.
- The Muse: The official API supports app display of Muse content through registered apps, and the API terms require application registration for compliant access and use. Unauthenticated technical access has a lower documented limit, but it must not be treated as production authorization. Registered applications must link Muse content back to The Muse, avoid scraping or cloning, comply with rate limits, and remove stored content if access is terminated.

These providers should still be disabled by default in production until Phase 15B adds adapter controls, attribution rendering, sync-run tracking, mocked tests, and a final terms review.

## 8. Conditional providers requiring keys, permission, or further checks

- Adzuna: API access requires `app_id` and `app_key`. Official terms allow publishing listings with required "Jobs by Adzuna" attribution, but default quotas are small and ongoing commercial, government, or academic use beyond the trial language may require written consent or a license.
- Jooble: A REST API exists and requires an API key, but official documentation found during this research does not clearly document display rights, attribution, cache retention, rate limits, or redistribution constraints.
- Greenhouse Job Board API: Public unauthenticated GET endpoints expose published jobs for a specific company board token. It is not a universal job-search API. Arclume should use only curated company board allowlists and seek company-level permission before storing or republishing listings beyond canonical links.
- Lever Postings API: Public published postings are namespaced by company site and available on global and EU endpoints. Frontend CORS is limited to the company's domains, so Arclume should treat this as backend-only and use a curated company allowlist. Storage and republication terms are not clearly documented.
- Codeforces: The official API exposes `contest.list` and anonymous access to public data with a documented request limit, but display, caching, attribution, and redistribution rights for Arclume are not clearly spelled out. Use metadata and canonical contest links only until clarified.
- Kaggle: The official CLI can list competitions and uses authentication for many operations, and Meta Kaggle exposes metadata, but competition-specific rules and platform terms mean Arclume should not treat competition data access as a blanket redistribution permission.
- Eventbrite: Official API documentation confirms REST access, OAuth/private-token authentication, and documented rate limits, but broad public event discovery and current API-specific display/caching terms require provider review before Arclume ingestion.
- Meetup: API access moved to GraphQL and is limited to approved OAuth consumers for active Meetup Pro members. API license terms prohibit commercial use without written consent and require privacy and storage controls, so Arclume needs approval before any production integration.

## 9. Manual curated official-link sources

The following sources are useful for Arclume users but should be represented as manually curated official links, not automated ingestion providers:

- Google for Developers Events, Google Developer Groups, and Google Developer Groups on Campus: Strong developer-community usefulness, including student relevance, but no supported public feed or redistribution model was found.
- GitHub Education and Student Developer Pack: High student usefulness, broad global availability, and many benefits, but best represented as a program link rather than ingested offer records unless GitHub provides an official feed.
- Microsoft Learn Student Hub and Microsoft Learn Student Ambassadors: Strong student and career-learning value, but no ingestion feed was found.
- AWS Educate: Useful for cloud learning and an authenticated job board for learners 18+, but the public source should remain a program link rather than an ingested job source.
- MongoDB student offerings, JetBrains Student Pack, Figma for Education, and Notion for Education: Useful benefit programs with official pages and eligibility rules, but no supported offer feed was found.
- Outreachy and Google Summer of Code: High open-source and student/fresher value. Use official program links and manually reviewed cycle metadata unless an official feed and terms approval become available.

## 10. Sources not approved for scraping

- LinkedIn: Official user agreement and crawling terms prohibit scraping or automated crawling without express permission and tightly restrict approved crawling use.
- Twitter/X: Official terms prohibit crawling or scraping the service in any form for any purpose without prior written consent. API use is governed by X's developer terms and automation rules.
- Instagram: Official help URLs were reachable only through Meta/Facebook login or restricted pages during this pass, so no usable public scraping authorization was found. Do not scrape Instagram.
- Devpost: Official terms prohibit manual or automated software, scripts, robots, scraping, crawling, or spidering of the site or related data. Devpost public listings are not approved for automated ingestion.
- Unstop: Undocumented public JSON endpoints are visible, but no current authoritative public developer documentation or display/caching terms were found. Do not scrape Unstop public listings.
- HackerEarth: Public hackathon listings are not backed by a suitable public discovery API or clear redistribution permission. Do not scrape HackerEarth public hackathon listings.
- Major League Hacking: The public event schedule is useful, but MLH terms limit site use to personal, non-commercial access and prohibit publishing, transmitting, reproducing, distributing, or publicly displaying content without written consent. Do not scrape MLH public listings.
- Random college posters and unofficial college pages: Exclude because authority, accuracy, copyright, freshness, and maintenance risk are too high. Official organizer or institution pages can be manually curated separately.

## 11. Recommended provider architecture

Phase 15B should implement backend-only provider adapters. The frontend must call only Arclume APIs and must never call third-party provider APIs directly.

Providers should be disabled by default unless explicitly activated. Credentials should come from environment variables or secret management, but credentials alone must not enable a provider. Greenhouse and Lever require provider allowlists of company board tokens or site names. Every adapter should normalize data into existing `jobs`, `hackathons`, and `student_programs` tables and preserve source metadata.

Standard source metadata should converge on `source_provider`, `source_id`, `source_url`, `last_synced_at`, and `attribution_label`. Where the current tables use `external_id`, `external_url`, `synced_at`, or `last_verified_at`, Phase 15B should decide whether to map those names or add fields only where necessary.

Add future sync-run tracking through an `opportunity_sync_runs` table with `provider_key`, `status`, `started_at`, `finished_at`, `records_fetched`, `records_created`, `records_updated`, and `sync_error`. Additional counters such as records deactivated, skipped, and failed would be useful if they fit the migration plan.

Adapters should use provider-specific polling intervals, idempotent upsert behavior, canonical source URL preservation, required attribution preservation, stale-record expiry or deactivation, HTML sanitization, bounded retries, timeouts, structured logs, and metrics that never leak provider credentials. Automated tests should use mocked HTTP responses and no live third-party API calls.

## 12. Attribution, caching, and rate-limit principles

Always show provider attribution when required and keep the original provider link visible. When provider terms require a backlink, use the canonical listing or event URL from the API response rather than an Arclume-only detail URL.

Cache conservatively. When storage terms are explicit, obey them. When storage terms are unclear, store minimal metadata, avoid full descriptions unless needed, use short-lived caches, and get provider approval before production. Do not redistribute imported listings to external job boards, search syndication feeds, or third-party APIs.

Rate-limit per provider rather than globally. Use a scheduler that can pause or disable one provider without affecting others. Keep polling slower than documented maximums. For providers without clear rate limits, use low-frequency sync, backoff, and provider contact before launch.

## 13. Phase 15B implementation plan

1. Audit existing normalized `jobs`, `hackathons`, and `student_programs` tables against the metadata fields listed above.
2. Add source metadata only where necessary and avoid unrelated schema churn.
3. Add sync-run tracking for provider observability and failure handling.
4. Define provider interfaces for fetch, normalize, upsert, deactivate stale records, and produce attribution metadata.
5. Define provider configuration and explicit activation rules.
6. Add normalization and deduplication contracts for source identity, canonical URLs, stale detection, and work-mode/category mapping.
7. Add mocked contract tests with recorded representative payloads and no live provider calls.
8. Implement Remotive as the first proof adapter because Arclume already has a Remotive sync path and Remotive has explicit API/RSS sharing rules.
9. Add operational documentation for credentials, activation, polling intervals, attribution UI, backoff, and incident handling.
10. Conduct a terms and attribution review before enabling any production sync.

Jobicy is a good second adapter candidate after the Remotive architecture proof. Adzuna, Eventbrite, and Meetup should wait for commercial/API approval. Greenhouse and Lever should wait for curated company allowlists and permission guidance.

- Keep all social, public hackathon, and unofficial sources out of automated ingestion unless an official API and explicit permission become available.
- Verify that automated tests use mocked provider HTTP and never call live third-party APIs.
- Verify logs, metrics, and errors do not expose provider credentials, tokens, or secrets.
- Review stale-record deactivation and retention behavior for each provider before launch.
